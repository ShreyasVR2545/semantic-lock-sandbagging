## Decision: **local**, 1.5B base retained, reduced grid

7.96 GiB places this machine in the brief's *6-8 GB, any cc* row, whose options are
"local with 0.5B base model, or Kaggle; prefer Kaggle if reachable". Neither option was
taken as written. See `DECISIONS.md` **D-002** for the full reasoning; in short:

- **Dropping the base to 0.5B would destroy the experiment.** The weak imitation target
  *is* Qwen2.5-0.5B-Instruct. A 0.5B base makes strong and weak the same model, the lock
  gap collapses to zero, and there is no capability left to lock or elicit.
- **Kaggle would stall the run.** The brief permits exactly one human checkpoint
  (Gate 2). The Kaggle path requires the user to log in, run a notebook and hand results
  back for stages 2-4, i.e. three more human checkpoints.
- **Measurement says 1.5B fits comfortably.** Empirically the 1.5B model in bf16 occupies
  2.88 GiB of weights and peaks at **3.31 GiB** during batch-32 generation - under half
  the card. LoRA training with gradient checkpointing has ample room.

### Measured generation throughput (Qwen2.5-1.5B-Instruct, bf16, greedy, 256 new tokens)

| Batch | tok/s | Peak VRAM |
|---|---|---|
| 8 | 230 | 2.98 GiB |
| 16 | 479 | 3.10 GiB |
| **32** | **829** | **3.31 GiB** |
| 64 | 969 | 3.73 GiB |

Batch 32 is the chosen eval batch size: 3.6x the throughput of batch 8, while batch 64
buys only 17% more and pays for it with more padding waste on heterogeneous real prompts.

### Resulting settings (`configs/hardware.yaml`)

```
execution: local          dtype: bf16 (guarded by is_bf16_supported)
base_model: Qwen/Qwen2.5-1.5B-Instruct    weak_model: Qwen/Qwen2.5-0.5B-Instruct
train batch 2 x grad-accum 4 (effective 8), gradient checkpointing on
eval batch 32
n_seeds: 2 (reduced grid)
```

Seeds were cut 3 -> 2 per the brief's budget rule (cut seeds first). This is the one
statistical-power cost of the 8 GB card and it is reported in the writeup's limitations.

## dtype guard

`src.utils.hardware.assert_dtype_supported()` is called at every training entry point and
raises if `hardware.yaml` requests bf16 while `torch.cuda.is_bf16_supported()` is False.
bf16 is never set from a config literal.

## Kaggle path: not selected

`notebooks/kaggle_runner.ipynb` and `KAGGLE.md` are **not** part of this run, since the
decision table selected local execution. If this repo is re-run on a machine the probe
routes to Kaggle, `src/utils/hardware.py` sets `execution: kaggle` and the orchestrator
prints instructions to generate those artifacts.

Note that only stages 2-4 (organism training, elicitation sweep, transfer) need a GPU.
Stages 5-6 (mechanistic analysis and figures) run from cached activations and CSVs and
are cheap enough to run on CPU.

## Compute budget

Target is under ~15 GPU-hours for the default grid. Per-stage wall-clock is logged to
`results/timing.csv` and summarised in `README.md` at the end of the run.
